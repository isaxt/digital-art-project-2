# The Office of Cultural Futures

A speculative web institution (a critical digital artwork) that registers artists, startups and institutions from cited public records, translates between art-world and startup vocabulary through explicit rules, and issues certificates whose provenance is recorded in a local hash-chained ledger.

Built to `Office_of_Cultural_Futures_Technical_Build_Spec.md` with the look from the visual-identity brief (blue institution, yellow classification, dense tables, monospaced data, dark ledger terminal).

## Run it

```bash
npm install
npm run dev          # http://localhost:5173
npm test             # 22 tests: engine, ledger, certificates, adapters
npm run build        # validates data, rebuilds seed ledger, typechecks, builds to dist/
npm run preview
```

`dist/` is plain static files with relative paths and hash routing, so it runs from any folder or static host (including an exhibition machine, offline).

## The dataset (read this)

**Real records only.** The Registry is built from two files you supplied, stored unchanged in `src/data/raw/`:

- `nyc_sf_contemporary_galleries.json`: 45 galleries and art spaces (rosters and current exhibitions where parsed)
- `nyc_sf_startups.json`: 99 startups (sector, accelerator, batch where recorded)

`npm run data:import` converts them into the app's model (`src/data/entities|sources|events.json`) and `npm run data:build` then validates, imports and rebuilds the seed ledger. The importer invents nothing: names, descriptions, URLs, IDs, statuses and notes are carried over as supplied; artists exist only because their exact name appears in a parsed roster or exhibition listing; unparsed rosters produce no artists; batches, dates, locations, representation and funding are never inferred. Tests in `src/services/engine.test.ts` re-check every imported record against the raw files.

Result: 277 entities (45 galleries, 99 startups, 133 artists), 214 source records, 215 events, 187 seeded certificates (issued only where at least one rule could read a recorded fact).

Things to know about the supplied data (also stated on the Methods page):

- `hashimoto_contemporary` appears twice in the galleries file (New York and San Francisco entries). Both are kept, unmerged, with the city appended to the registry ID; the original ID is shown as "Dataset ID".
- 42 of 45 galleries have rosters "not yet parsed" and 32 have no exhibitions verified (parsed); the UI says unknown, never "none".
- Marian Goodman's only listed exhibition is at a Paris venue; Kiang Malingue's note says it has Hong Kong and New York spaces. Both are displayed as supplied.
- The startups file says "100" in its description but contains 99 records (its `record_count` is 99).
- The dataset's startup batches are marked "recorded from known program history", and accelerator directory links are city/portfolio level, so startups are at most PARTIAL.
- Exhibitions are "current" as of 2026-11-07 and will go stale (one ends that same day).
- The earlier seven hand-gathered records (Kara Walker, Dropbox, etc.) came from automated page summaries, not from your files, so they were moved out of the live data into `src/data/_unverified_pre_dataset/` (see its README).

To add records later they must come from identifiable real sources with URLs and a verification status.

## Ledger in one paragraph

`eventHash = SHA-256(canonical(event fields) + "|" + previousEventHash)`. Seed events are built by `scripts/buildLedger.ts` (fixed timestamps, derived IDs, byte-reproducible). Events a visitor creates (certificates, corrections, disputes) are appended in that browser's localStorage after the seed chain and are never sent anywhere. The chain is verified from the first event on every load. It is a local simulation and the UI says so everywhere; it is not decentralized, trustless or immutable.

## Block explorer and chain devices
Routes: `/explorer`, `/block/:height`, `/tx/:id`, `/address/0x…`, `/contract`. Mining happens on the Translation page (mempool → difficulty slider → nonce search → certificate); confirmations and witnessing are on each certificate. Logic: `src/services/chainService.ts` (tests in `chain.test.ts`). Tunables in `src/config.ts` (`blockSize`, `finalityDepth`, `quorum`, `miningDefaultDifficulty`). All of it is derived from the local ledger; it is a simulation, not a blockchain.

## Environment variables

None are needed to run the site. `.env.example` lists optional keys for ingestion (`COMPANIES_HOUSE_API_KEY`, `SEC_USER_AGENT`); they are only read by Node scripts and never reach the browser bundle.

## Before exhibiting

- Set `correctionsContact` in `src/config.ts`.
- Have a person verify the dataset records (the datasets themselves mark many sections unverified or not yet parsed).
- Replace the placeholder emblem (`Emblem` in `src/components/shared/index.tsx`) with the final mark.
- Check each source's terms for any reuse beyond the short factual fields stored.

## Orientation and Archive

On first visit a two-step orientation window explains the concept, then shows the original Substack post (scrollable). It can be reopened from the header, footer or Archive. The Archive keeps the post as a reference. The article text lives in `src/data/articles/parallels.txt` (set `complete: true` and `url` in `articles.json` once the full text and link are added).
